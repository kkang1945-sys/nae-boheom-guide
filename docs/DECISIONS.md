## D-028 제출 화면은 결론과 증권 사실을 우선한다

- 날짜/상태: 2026-10-08 / 테스트 완료
- 결과 첫 화면은 확인된 진단비와 비상자금으로 필수생활비를 유지할 수 있는 기간을 한 문장으로 제시한다. 동일한 계산 구조의 질병 카드는 하나로 묶고 질병별 금액은 펼쳐보기에 둔다.
- 상단 요약은 생활비 유지 기간·확인한 보험증권 수·계산한 질병 상황 수처럼 서로 의미가 분명한 사실 지표만 사용한다. `증권 표기 없음`은 보장 부재로 오해되지 않도록 `현재 증권에서 찾지 못함`으로 표현한다.
- OCR 지급조건과 개발용 검산·재추출·수정·삭제 기능은 삭제하지 않고 각각 `추출한 지급조건 보기`, `고급 관리` 안에 둔다. 기본 화면은 쉬운 설명·금액·증권 이미지 원문 링크만 보여준다.
- 이 단순화는 계산 안전장치나 원문 보존을 완화하지 않는다. 미확정 보험금을 계산에 합산하지 않고 실제 지급 여부도 확정하지 않는다.

## D-024 같은 계약 조회자료의 대상자 일괄 연결

- 날짜/상태: 2026-09-15 / 테스트 완료
- 부분 마스킹 계약 식별값과 상품명의 해시 지문으로 이미 같은 계약임이 확인된 조회자료는 대상자 설정 화면에서 한 묶음으로 표시한다. 사용자가 `같은 계약 자료 모두 연결`을 명시적으로 선택할 때만 묶음 전체를 한 대상자에게 연결한다.
- 일반 문서와 단일 조회자료는 기존처럼 개별 연결한다. 해시 지문 자체는 화면에 표시하지 않으며 대상자를 추측하거나 자동 생성하지 않는다.
- 같은 계약 묶음의 동일 위험 담보가 여러 파일에 겹치면 자금공백 대응금액으로 중복 합산하지 않고 판단을 보류한다. 계약 요약 금액을 지급 담보로 승격하지 않는 D-023 원칙은 유지한다.
- 실제 대상자 선택은 사용자 확인이 남아 있다.

## D-023 이미지형 웹 조회자료의 계약 묶음과 보장 분리

- 날짜/상태: 2026-09-14 / 테스트 완료, 사용자 메타정보 확인 전
- 교보생명 웹 조회형 PDF는 직접 PDF 글자에 포함된 공식 조회 경로로 형식을 식별하고 모든 페이지를 로컬 OCR한다. 부분 마스킹 증권번호 원문은 저장하지 않고 보험회사·상품명과 함께 만든 SHA-256 지문만 저장해 계약정보·가입특약·보장내역 파일을 한 계약으로 묶는다.
- 가입특약 조회의 주계약·특약 가입금액과 기간은 `contract_summary`로 보존하며 보험금 지급 담보로 승격하거나 자금공백 계산에 사용하지 않는다. 보장내역은 항목명·금액·보장내용이 같은 화면 구역에 있을 때만 `benefit_detail` 후보로 만든다.
- OCR의 점·슬래시·한글 글자 혼동은 고정 조회 레이아웃의 좌표와 독립 금액 파서가 모두 일치할 때만 보정한다. `1회`·`1일당`·`120일 한도`의 숫자를 보장금액에 합치지 않는다. 불일치하면 행을 만들지 않고 `확인 필요`로 남긴다.
- 90일 책임개시와 계약일 2년 이내 일부 급부 50% 감액은 명시된 중요안내 구역의 원문 근거로만 연결한다. 만기급여금·생존연금·공시이율·계약자적립금 안내는 위험보장 담보와 분리한다.
- Tesseract TSV는 CSV 인용 규칙이 없는 탭 구분 출력이므로 따옴표를 CSV quote로 해석하지 않고 행별 탭 분리한다. 기존 OCR 캐시는 파서 버전 `local-tesseract-tsv-v3`으로 갱신한다.

## D-022 보험회사·상품 후보와 표 밖 조건 범위

- 날짜/상태: 2026-09-10 / 테스트 완료
- 보험회사 후보는 주소·대리점명에 포함된 다른 보험회사 문자열보다 증권의 `발행자`, `보험회사`, `회사명`처럼 역할이 명시된 직접 PDF 글자를 우선한다. 기존 기계 후보가 잘못됐으면 새 근거로 교체하되 사용자 확정값과 확인 이력은 변경하지 않는다.
- 상품명은 `상품명:` 표기, `무배당`으로 시작하는 짧은 보험 상품 제목, 기존의 명시적 상품 코드 패턴만 후보화한다. 일반 보험 안내 문장은 상품명으로 사용하지 않는다.
- 가입금액 칸과 지급 문구가 있고 실손·한도 보상·배상책임 문구가 아닌 경우에만 정액형 후보로 분류한다. `1사고당`은 원문에 명시된 사건별 지급으로 분류한다. 갱신 문구가 없는 담보를 비갱신으로 추측하지 않는다.
- 표 머리글, 예금자보호, 만기환급·중도인출, 청약철회 같은 계약 행정 안내는 보장조건 후보에서 제외한다. 표 밖 조건은 계약 전체, 실손·간병 등 특정 담보, 행정 안내를 구분하며 `특정 담보에 적용·연결 확인 필요` 상태는 분석 차단을 유지한다.

## D-013 실제 PDF 담보 후보와 사용자 이력

- 날짜/상태: 2026-09-03 / 테스트 완료
- 기존 HWPML 담보 스키마의 필수 Boolean 갱신값에 PDF 미확인값을 억지로 저장하지 않는다. `PdfCoverage`에 명시된 값·unknown·원문 셀 좌표를 별도로 저장하고 추출값과 사용자 값을 분리한다.
- `PdfExtractionRun`에 추출기 버전·행 수·표 식별 경고를 기록하고 `PdfCoverageRevision`에 사용자 저장 전후를 보존한다. 추후 통합 시 공통 규격으로 변환하며 이 단계에서 두 문서 형식을 합산하지 않는다.
- 마지막 쪽의 외곽선 생략은 앞쪽에서 검증한 열 좌표와 현재 표 제목 위치가 일치할 때만 보완한다. 표 뒤 안내문은 제목 경계로 제외한다.
- 회사 로고만 있고 직접 읽히는 회사명이 없는 경우 추측하지 않는다. 사람의 원문 확인과 앱의 자동 추출 상태를 구분한다.

- PyMuPDF를 필수 의존성으로 올리고 프로젝트 전용 `.venv`를 실행 시 우선 사용한다.
- 페이지 글자·단어 좌표·크기·회전·추출기 버전을 별도 테이블에 저장한다. 기존 담보·사용자 확정값은 변경하지 않는다.
- 글자 읽기 성공과 담보 추출·정확도 확인을 구분하며, 이미지 혼합 페이지의 누락 가능성과 OCR 필요 상태를 표시한다.

- Windows에서 손상 PDF를 읽다 실패해도 임시 파일을 지울 수 있도록 파일 바이트로 읽는다.
- 실제 PDF·OCR 검수와 담보 구조화는 별도 남은 작업이다. 상세는 `PDF_EXTRACTION.md` 참조.

## D-001 구현 스택과 실행 형태

- 날짜/상태: 2026-09-02 / 사용자 확인 완료
- 개인 PC에서 실행하는 로컬 우선 웹앱과 단일 저장소로 시작한다.
- 처리 서버는 Python/FastAPI, 로컬 데이터 저장은 SQLite와 관리되는 파일 폴더를 사용한다.
- PDF 텍스트·페이지 처리는 PyMuPDF를 사용하고, 텍스트가 없거나 품질이 낮은 페이지만 Tesseract로 OCR한다. OCR 결과는 페이지별로 저장해 반복 실행하지 않는다.
- 추출은 `직접 텍스트 → 필요한 페이지의 로컬 OCR → 규칙 기반 구조화 → 사용자 확인·확정` 순서로 처리한다.
- 2026-09-03 D-014로 확인 절차를 갱신했다. 검증 범위가 충족된 핵심값만 분석에 사용하며 현재 표 읽기 검산은 분석용 조건 확인을 대신하지 않는다.
- 외부 OCR/AI 전송은 기본 비활성이다. 로컬 방식으로 해결하기 어려운 일부 항목에 대해 개인정보 제거, 전송 범위·보관·삭제 조건 확인과 사용자 명시 동의가 모두 있을 때만 별도 기능으로 검토한다.
- 화면은 FastAPI의 Jinja2 서버 렌더링과 소량의 일반 JavaScript로 구현한다. 별도 Node/SPA 빌드 체인은 두지 않는다.
- 데이터 모델·검증은 Pydantic과 SQLAlchemy 2.x, 스키마 변경은 Alembic 마이그레이션으로 관리한다.
- 데이터 변경은 명시적 트랜잭션으로 처리하고, 원본 파일 작업과 DB 상태가 어긋나면 복구 가능한 실패 상태를 남긴다.
- 테스트는 pytest 단위·통합 테스트를 기본으로 하고, 핵심 사용자 흐름은 Playwright 브라우저 테스트로 검증한다.
- 화면, PDF 처리, 담보 규칙과 계산 엔진을 모듈로 분리해 나중에 공개 배포용 화면이나 PostgreSQL로 교체할 수 있게 한다.

## D-014 업로드 후 자동 검토·검산과 예외 확인

- 날짜/상태: 2026-09-03 / 사용자 확인 완료(절차 변경 요청), 구현은 아래 범위 테스트 완료.
- 사용자가 한 번 업로드하면 앱이 먼저 검산한다. 모든 담보를 사용자가 확인해야 하는 기존 절차를 바꾸고, 해소하지 못한 불일치·추가 자료만 확인하도록 한다. 편집 기능은 유지한다.
- 첫 검산은 PyMuPDF 추출 결과와 독립적인 pdfplumber/pdfminer 읽기를 비교한다. 네 셀 텍스트, 별도 정수 금액 변환, 납입/보험기간 재결합, 원문 머리글에서 독립 탐색한 금액 수·행 대응을 검사한다.
- `PdfAudit`에 원본 해시·입력 지문·두 읽기 엔진과 검증기 버전·결과를 저장한다. 원본 또는 값 변경 시 이전 기록은 재사용하지 않는다. 동일 입력은 재사용하며 원본/문서 전체 삭제 시 연관 기록을 삭제한다.
- 사용자 확정값과 자동 검산을 구분한다. 자동 검산은 `confirmed_fields`/사용자 확인 상태를 변경하지 않는다. 별도 사용자 수정값이 있어도 표 요약에는 원문 검산값을 명확히 표시한다.
- 첫 관문 통과는 인식된 4열 표의 전사·금액·기간 검산에만 해당한다. 전체 문서 누락 없음, 의미 해석 정확도, 지급 가능성 또는 분석 준비 완료로 확대하지 않는다. 두 엔진의 일치도 독립적인 정답 증명은 아니다.
- 2026-09-08 현재 `analysis_ready`는 표 검산, 대상자·계약 메타정보, 담보 조건 근거와 핵심 의미값이 모두 확인되고 문서 범위 후보가 해소된 경우에만 True가 된다. 사용자 전수 확인이나 자동 추출만으로 관문을 우회하지 않는다.
- 외부 OCR/AI 전송은 비활성 유지. 새 기술 결정으로 pdfplumber 0.11.9 이상 0.12 미만을 로컬 의존성에 추가했다. 현 기능은 로컬 읽기·규칙 검산이며 LLM 검토 API가 아니다.

## D-018 위험별 부분 계산 관문

- 날짜/상태: 2026-09-15 / 테스트 완료
- 문서 전체의 모든 담보가 확정될 때까지 모든 결과를 막지 않는다. 대상자·생애단계 경제정보·보험회사/상품·원본 해시 연결과 문서 공통조건이 준비되면 담보별 관문으로 전환한다.
- 개별 담보는 사용자 확정값, 독립 원문 검산, 해당 페이지 텍스트/OCR, 보장내용 원문 근거가 모두 준비된 경우에만 계산한다. 다른 담보의 미확정 의미값은 이 담보의 계산을 막지 않는다.
- 문서 전체에 적용될 수 있는 공통조건의 범위가 미확정이거나 같은 계약 중복 가능성이 있으면 기존처럼 계산을 차단한다. 미확정·실손·복합 범위 담보를 현금처럼 합산하지 않는다.
- 사용자 확인은 원문에서 확인되는 값에만 적용한다. 지급횟수 등 원문에 없는 의미값을 편의를 위해 임의 확정하지 않는다.
- 같은 계약 중복 차단은 동일 분석 대상자에게 연결된 문서끼리 적용한다. 대상자에 연결하지 않은 보관·형식검증 문서는 다른 대상자의 계산을 막거나 합산에 참여하지 않는다.
- 대화에서 결과 예시를 위해 제시한 경제조건은 모의계산 입력으로만 사용하며, 사용자가 실제 저장값이라고 명시하지 않으면 대상자·경제정보 DB에 저장하지 않는다.

## D-019 의료기간과 시장 평균의 보조 사용

- 날짜/상태: 2026-09-15 / 사용자 확인 완료
- `사망 후 가족생활비를 준비할 기간`은 입원기간이 아니다. 사용자가 가족 상황에 따라 선택하며 평균 입원일수로 자동 지정하지 않는다.
- 심평원 질병 입원외래·성별연령별 통계는 질병·연령별 의료이용 참고자료로 표시할 수 있지만, 평균 입원일수를 치료기간·휴직기간·소득중단 기간으로 자동 변환하지 않는다.
- 시장 비교자료가 확보되면 출처·기준연월·모수·단위를 표시한 보조지표로만 제공한다. 계약 1건 평균을 개인 1명의 총보장 평균처럼 표현하거나 평균 미만을 부족으로 판정하지 않는다.
- 부족 여부의 핵심 기준은 계속해서 사용자의 부채·가족생활비·사용할 자산과 확인된 보장의 차액이다.
- 사망 결과에는 부족액과 별도로 `부채 상환 전/후 생활비 충당 개월 수`를 표시한다. 공적 비교선은 사망 후 남는 가구원 수에 따른 해당 연도 생계급여 최저보장수준을 사용하고, 출처·기준연도·한계를 함께 노출한다.

## D-020 비저장 모의계산과 사망보장 확인 상태

- 날짜/상태: 2026-09-15 / 테스트 완료, 사용자 화면 확인 전
- 모의계산은 선택한 PDF와 현재 요청의 경제조건만 사용한다. 대상자·경제정보·결과 스냅샷을 DB에 생성하지 않고 저장·내보내기 동작도 제공하지 않는다.
- 문서의 대상자 미연결만 모의계산 요청에서 대체한다. 원본 해시, 메타정보, 표 검산, OCR, 공통조건과 행별 근거 관문은 기존대로 유지한다.
- 일반·질병 사망과 상해 사망을 계산 완료·미확정 후보·업로드 증권에서 찾지 못함으로 나눈다. 복합 사망/후유장해 명칭은 검토 후보로는 보여도 확정보험금으로 정규화하거나 계산에서 차감하지 않는다.
- 보험금이 미확정이어도 사용자가 부채·가족생활비·준비기간·사용할 금융자산을 입력하면 가족 필요자금은 별도 계산한다. 이 금액은 개인 시나리오이며 가입 권장액 또는 확정 부족액이 아니다.

## D-021 심평원 질병 의료이용 통계 연동

- 날짜/상태: 2026-09-16 / 구현·합성 응답 테스트 완료, 실제 키 호출 전
- 서비스 키는 `HIRA_DISEASE_API_KEY` 사용자 환경변수에서만 읽고 코드·DB·캐시·화면·로그에 기록하지 않는다. Encoding/Decoding 키를 모두 받아 내부에서 한 번만 URL 인코딩한다.
- 외부로 보내는 값은 질병코드·통계연도와 심평원 명세상 고정 구분값뿐이다. 보험증권·대상자·경제정보를 전송하지 않는다.
- 입원·외래별 통계와 성별·연령별 통계를 XML로 읽고 공개 응답만 PC의 `data/public_cache/hira_disease/`에 7일 캐시한다. 오류나 미설정 상태는 보험 자금공백 계산을 막지 않는다.
- 통계는 의료이용 참고정보이며 평균 입원일수를 개인 치료기간·휴직기간·소득중단 기간이나 보험 가입 필요액으로 변환하지 않는다.

## D-025 제출 범위에서 생성형 AI 연동 제외

- 날짜/상태: 2026-10-07 / 사용자 확인 완료
- Gemini API 기반 `AI 종합 설명`과 `내 보험에 물어보기` 기능은 이번 작품 제출 범위에서 제외한다.
- 현재 코드에는 Gemini 연동이 없으므로 별도 제거 작업은 없다. 제출 버전에 생성형 AI SDK, API 키, 외부 전송 경로를 추가하지 않는다.
- 보험증권의 추출·검산·계산·쉬운 설명은 기존 로컬 규칙과 원문 근거로 처리한다. 보험증권과 개인정보를 외부 생성형 AI로 전송하지 않는다.
- 확보한 작업 시간은 입원 생활자금 계산, 계산 외 보장 요약, 실제 증권 회귀 테스트, 시연 안정화와 제출 문서 정리에 사용한다.

## D-026 입원 생활자금 계산 경계

- 날짜/상태: 2026-10-07 / 테스트 완료, 사용자 화면 확인 전
- 입원·휴직 기간은 앱이 추천하지 않고 사용자가 0~24개월에서 직접 선택한다. 0개월이면 입원 생활자금 계산을 생략한다.
- 필요자금은 선택 기간의 월 필수생활비와 사용자가 입력한 추가비용으로 계산한다. 입원 중 유지되는 월 소득, 유급휴가·회사 지원, 사용할 비상자금과 확인된 입원급여를 사용 가능 자금으로 분리해 계산식에 공개한다.
- 입원급여는 사용자 확인 완료, 원문 검산 완료, 정액형, 1회 지급, 보험기간 확인 조건을 모두 만족할 때만 금액에 반영한다. 일당형·반복형·실손형·미확정 담보는 합산하지 않고 계산 외 보장 요약에 표시한다.
- 입원 계산과 진단비·사망 계산은 각각 독립 시나리오로 유지하며 서로 다른 사고·질병 보험금을 하나의 확정 현금처럼 합산하지 않는다.
# D-027 제출용 기본 흐름은 짧게, 상세 보장은 증권 표기로 제공

- 날짜: 2026-10-08
- 상태: 채택
- 결정: 통합 화면은 증권별 주요 보장 5개만 보여주고 상세 버튼은 결과 하단으로 이동한다. 모의계산 기본 입력은 월 필수생활비·비상자금·남은 대출·부양가족 4개로 제한한다. 결과의 긴 설명·확인 필요 타일·계산 외 보장 목록은 제거하고, 입원·통원·수술을 별도 화면에서 보험별 증권 표기 그대로 제공한다.
- 이유: 제출 시 핵심 흐름을 짧고 이해하기 쉽게 유지하면서도, 불확실하다는 이유로 실제 증권 정보를 대부분 숨기지 않기 위해서다.
- 안전 경계: `증권에서 읽은 내용`과 `사용자 확인`을 구분하고 원문 링크를 제공한다. 미확정·실손·반복 지급 담보를 자금공백 계산에 임의 합산하거나 실제 지급액으로 확정하지 않는다.
